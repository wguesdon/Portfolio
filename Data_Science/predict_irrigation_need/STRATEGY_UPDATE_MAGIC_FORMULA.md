# Strategy Update: The "Magic" Original Data Formula

## Discovery

On April 3, 2026, it was discovered in the competition discussions (`PS6E4/discussions/original_data_formula.md`) that the original 10,000-row dataset (`irrigation_prediction.csv`) is completely deterministic. It was generated using a strict, rule-based formula that perfectly separates the classes (Balanced Accuracy = 1.0 on the original data).

The logic computes a score based on continuous and categorical thresholds:

```python
# The "Magic Score" Formula
High_score = (Soil_Moisture < 25) * 2 + (Rainfall_mm < 300) * 2 + (Temperature_C > 30) * 1 + (Wind_Speed_kmh > 10) * 1
Low_score = (Crop_Growth_Stage == 'Harvest') * 2 + (Crop_Growth_Stage == 'Sowing') * 2 + (Mulching_Used == 'Yes') * 1

magic_score = High_score - Low_score

# Perfect Mapping in Original Data (10k rows):
# magic_score <= 0      -> Low (0)
# 1 <= magic_score <= 3 -> Medium (1)
# magic_score >= 4      -> High (2)
```

## Impact on the Synthetic Data (The "Blur" Effect)

The competition evaluates us on the 630K **synthetic dataset**. Because the synthetic data was generated by a deep learning model (like CTGAN) trained on the original data, this strict formula will **not** perfectly predict the synthetic labels.

The synthetic generator "blurred" the sharp decision boundaries:
1. **Continuous Perturbation:** An original value of `Soil_Moisture = 24.0` (Triggering the `< 25` rule) might be perturbed to `25.1` in the synthetic data. The formula would score this differently, but the generator might still assign it the label corresponding to the original `24.0`.
2. **Label Noise:** The generator likely learned a probability distribution rather than a strict if/then rule, introducing random class flips.

## Updated Strategy

Finding the exact generating formula for the original dataset is a game-changer. We no longer need to rely purely on brute-force feature generation (like our current 516 features). Our GBDTs should no longer spend hundreds of splits trying to deduce the agricultural logic; we can feed them the exact blueprint.

### 1. Feature Engineering Refinements

We must immediately incorporate this logic into our feature store (`aws/features.py` and local scripts).

*   **Raw Magic Score:** Calculate `magic_score` directly on the raw synthetic numeric values.
*   **Snapped Magic Score (The Secret Weapon):** Because our Phase 2 strategy already involves calculating "snap features" (mapping noisy synthetic numbers back to the discrete original 10K values), we must calculate the `magic_score` using the **snapped** versions of `Soil_Moisture`, `Rainfall_mm`, `Temperature_C`, and `Wind_Speed_kmh`. This reconstructs the "True Magic Score" of the row before the generator added continuous noise.
*   **Boolean Flags:** Expose the individual rule components as binary features (e.g., `is_soil_dry_raw`, `is_soil_dry_snapped`).
*   **Target Encoding Anchor:** The `magic_score` (ranging from -3 to 6) is an incredibly powerful categorical anchor. We should perform nested Target Encoding grouping by `magic_score`.
*   **Feature Pruning:** With this deterministic signal, many of our 516 domain arithmetic and cross-features are likely redundant noise. We should experiment with drastically reducing the feature count (e.g., top 100) to prevent overfitting on the rare High class.

### 2. Modeling Adjustments

*   **The Goal of the Model Shifts:** The GBDTs (XGBoost, LightGBM, CatBoost) and NNs no longer need to learn the basic rules of irrigation. Their primary job is now to learn **how the synthetic generator made mistakes** (the perturbation noise and the probability blur around the boundaries).
*   **Tree Depth:** Because the primary logic is pre-calculated, we might be able to reduce `max_depth` in our GBDTs, as they need fewer splits to refine the decision boundaries.
